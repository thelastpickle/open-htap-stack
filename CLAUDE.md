# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A runnable demonstration that one Cassandra dataset can serve transactional and analytical work without ETL copies, and that analytical scans need not touch the OLTP request path. Everything here exists to make that claim checkable, so **a change is not finished until it has been run against the stack and measured**. Numbers in the docs, the PR body and the UI copy are measurements from a real run, not estimates; if you cannot measure a claim, do not make it.

## The five access paths

The same rows are reachable five ways, and the difference between them is the whole point of the demo. Every part of `backend/app/db/` and the compare page exists to keep them comparable:

| Path | Route | Property it demonstrates |
| --- | --- | --- |
| `cassandra` | CQL request path | point/bounded reads; **declines** what CQL cannot express (no `GROUP BY` on a non-key column) |
| `presto` | Presto → Cassandra connector → CQL | full SQL, distributed scan, still over the request path |
| `spark` | Spark Thrift Server → spark-cassandra-connector → CQL | batch SQL over the request path |
| `spark_bulk` | Spark Thrift Server → Cassandra Analytics → Sidecar → SSTable files | reads a coordinated snapshot directly; **cannot** contend with OLTP; rows are as of the snapshot, not now |
| `cqlite` | DataFusion → cqlite → the live SSTable files, in the backend process | reads the files where they lie: no snapshot, no Sidecar and no JVM; **cannot** contend with OLTP; rows are as of the last flush, so what is still in a memtable is not read |

Cassandra failing a query is often the correct, interesting result. Do not "fix" it by widening the SQL — the refusal is the finding, and the UI reports it as a decline rather than an error.

## Skills

`.claude/skills/` holds the four procedures that are easy to get subtly wrong; read the relevant one before starting rather than after.

| Skill | Read it when |
| --- | --- |
| `stack` | bringing the stack up, getting a code change into a running service, or reading a container failure |
| `ci-step` | before pushing a workflow change, or to run the failing CI assertion locally |
| `measure` | before quoting any number, or when explaining why one path beat another |
| `schema` | before changing a table, or when a query silently returns nothing |

## Commands

Everything runs under podman-compose. `compose.yml` is a symlink to `podman-compose.yml`; edit the latter.

```bash
# whole stack (needs a podman machine with >12 GB)
podman compose -f podman-compose.yml up -d

# rebuild and restart one service after a code change
podman compose -f podman-compose.yml build backend frontend
podman compose -f podman-compose.yml up -d --no-deps backend frontend

# wipe data and schema (stops everything, deletes cassandra-data/)
./stop-and-clean-data-and-schema.sh
# truncate the demo tables but keep the stack up
./scripts/cleanup-data.sh
```

Frontend: `cd frontend && npm run build` — this runs `tsc -b` first, so it is the typecheck. `npm run dev` proxies `/api` to `localhost:8000` (`VITE_API_PROXY` overrides).

Backend: no test suite. `python3 -m py_compile backend/app/**/*.py` is the syntax check; correctness is verified by running queries against the stack. To run the backend on the host instead of in the network, set `CASSANDRA_TRANSLATE_ADDRESSES_TO=127.0.0.1` — otherwise the driver discovers `172.20.0.10` and cannot reach it.

Rust: no Rust is built here.  The cqlite reader's source lives in the cqlite fork; `cd ~/src/mck/cqlite/cqlite-datafusion && cargo test --all && cargo fmt --all --check && cargo clippy --all-targets` — 38 unit tests and a doctest, in about a second.  There are **no** fixture SSTables: every test is over a synthetic schema or a temporary directory, so anything about reading real files is verified by running a query against the stack.  A reader change reaches this stack through `scripts/build-cqlite-wheel.sh`; see `backend/dist/VENDOR.md`.

Ports: dashboard `4000`, backend API and `/docs` `8000`, Cassandra `9042`, Sidecar `9043`, Presto `8088`, Spark master UI `8080`, Spark application UI `4040`, Thrift Server `10000`, Kafka `9092`, cassandra-sql's Postgres wire protocol `5432`.

## Testing

There is one test suite and it is `.github/workflows/test-podman-compose.yaml`: a single job that builds the stack, waits on each service, then asserts behaviour through the CLIs and the dashboard API. The "Test Mission Control dashboard" step is the largest and covers the five paths.

CI is slow (~15 min to a first failure) and podman on the runner has no systemd, so healthchecks never leave "starting" — the workflow does its own ordering and waiting rather than trusting `depends_on: service_healthy`. **Run a step locally before pushing**; see the `ci-step` skill, which extracts a step from the YAML and runs it verbatim against the running stack.

Assertions must be structural, not timing-based, and must hold on a stack that is minutes old with data still arriving. A fresh CI stack has no closed 15-minute window, small tables, and a growing Kafka backlog; assumptions that hold on a laptop that has been ingesting for an hour do not hold there.

**A build-time download must carry a checksum, and a download nothing needs must be opt-in.** CI failed on `ingress/producer/Dockerfile`'s unconditional 322 MB `enwik9.zip` fetch: `wget -qc` wrote a file in 150 ms and exited 0, where the same step had taken 13.7 s and succeeded six hours before, so the host answered that runner with something short and the build died one step later at "unzip: cannot find zipfile directory". Three build attempts could not help, because the bad download sat in a layer the second and third reused, and `-q` had discarded whatever the server said. So the fetch is now one `RUN`, checksummed, and behind `--build-arg FETCH_ENWIK9=1`: `wikipedia.txt` is the default corpus and enwik9 serves only volume testing, which takes 1.0 GB off the image, 280 MB against 1.28 GB. Every other download in every other image already verifies a checksum; keep it that way.

## Architecture notes that span files

**The demo schema is owned by the sink**, `ingress/consumer/consumer.py:ensure_schema()`, not by any migration. See the `schema` skill before changing it: a rebuild alone will not apply a new key.

**`demo.events` is partitioned by time**: `PRIMARY KEY ((event_bucket, shard), event_id)`, where `event_bucket` is a 15-minute UTC window as text and `shard` is `crc32(event_id) % 16`. Bucket width and shard count are declared once in `podman-compose.yml` and read by both the sink and the backend (`EVENT_BUCKET_MINUTES`, `EVENT_SHARDS`); the two disagreeing produces queries that match nothing. Text rather than a timestamp so one literal parses in CQL, Presto SQL and Spark SQL alike.

**The stack ships at 5 events a second, and every figure in these docs was taken at 2,000.** Nothing downstream of the generator bounds the data: Kafka's retention holds some 12 GiB, `cdc_raw` holds 4 GiB, and Cassandra's own data directory has no bound at all, so a stack left running at 2,000 a second fills a laptop's disk in an afternoon, which is what killed two of them. The rate is therefore turned up on the Settings page for the run being shown, and `DEMO_EVENTS_PER_SEC` in `.env` is the startup value; that file is committed, and compose reads it, so a shell variable is what overrides it. `.github/workflows/test-podman-compose.yaml` sets `DEMO_EVENTS_PER_SEC: "2000"` in the job's environment for exactly that reason: every assertion in it was written against a stack ingesting hard, and at 5 a second none of them would have data to read within the job's 45 minutes. **Quote a figure with the rate it was taken at**, and do not read the shipped default as the rate a measurement was made under.

**The send loop carries a fractional event, because flooring each turn put a floor under the rate.** The loop runs every 50 ms, so 5 a second is a quarter of an event a turn, and the `max(1, int(eps * period_s))` that preceded it sent one every turn and so ran at 20 a second while its own report line said 5. Four times the requested rate was invisible until the default came down to 5. `producer.py` keeps an `owed` accumulator instead, and a turn may now send nothing, which the loop guards rather than passing on, because `stamp_step_s` divides by the batch size. What is carried is below one event, so a rate the Settings page changes takes effect on the next turn and no burst of the old rate survives it. The frontend's slider has a floor of 5 for the same change: at 50 the thumb sat at its minimum while the readout said 5, and the first drag raised the rate to a value nobody had asked for.

**A closed window is not a finished one, and the sink's Kafka offsets are what tell them apart.** Because `event_bucket` comes from the event's own timestamp, a sink behind the topic keeps inserting into windows the clock has passed, and the paths then disagree on a window that has closed: CI failed three times on 80,810, 81,697 and 82,869 rows from the three analytical paths, while the sink ran some 645,900 records behind a producer at 1,899/s against its own 712/s. `_sink_consumed_past` in `backend/app/routes/query.py` answers it from the sink's committed offsets, comparing each against `offsets_for_times(window end + 60 s)` and requiring **every** partition to pass. Requiring every one is the fix: the sink polls with `max_poll_records` across the topic's twelve partitions, which `ingress/producer/producer.py` creates explicitly over the broker's `KAFKA_NUM_PARTITIONS` of 3, so under a backlog their positions diverge widely and one partition reaching the current window says nothing about the other eleven. Asking Cassandra whether the window now filling holds a row is that mistake, and it reported settled while the closed window grew by 3,673 rows over the next 70 s. The flag may be read before a comparison and trusted after it, because a sink that has consumed past a window's end can never write into that window again. It is not a zero-lag test: on one run it turned true the moment the last partition crossed the window's end, with 552,300 records of lag still outstanding, and all four paths then returned 444,625 exactly. It costs `/api/query/window` about 550 ms against 20 ms, 520 ms of which is opening the two Kafka clients, and one client cannot do both jobs: a consumer carrying the sink's group refuses a request timeout below its 10 s session timeout, then blocks past 74 s inside `committed()` with no assignment. Four simpler gates were measured and rejected. Total lag reaching zero never fires on a runner whose sink does 712/s against 2,000/s, so the assertion would never run; a `COUNT(*)` over one bucket's sixteen shards is refused with `ReadTimeout` code 1200, which rules out counting the window before and after the run; lowering the producer's rate in CI is a race rather than a guard, and it removes the write contention the comparison exists to show; and pausing the producer to drain needs a flush before cqlite can agree, and measures point reads with no concurrent writes.

**The Spark container holds both Spark package sets in one JVM.** `spark/install-cassandra-libraries.sh` puts the connector and Analytics jars on the *system* classpath before the Thrift Server starts; `--packages` would put them on the application classloader, where the driver's `reference.conf` is invisible to the config-reload thread and schema resolution wedges after 5 minutes. The Thrift Server also gets its own Derby metastore and a `spark.cores.max` cap so it cannot starve `spark-sql` jobs run beside it in the same container.

**The bulk reader takes a snapshot per read.** `backend/app/db/spark_client.py` derives the snapshot TTL from `spark_query_timeout_s` — Cassandra expires a snapshot on time regardless of who is reading, and a read that loses its snapshot mid-scan fails with "Required 1 replicas but only 0 responded". A caller may reuse the last snapshot (`reuse_snapshot`), which is refused when too little TTL remains. Registering the view and running the statement are one locked operation, because the view name is per-table and a second query would otherwise replace the first's snapshot mid-flight.

**The cqlite reader arrives as a prebuilt wheel, and its source lives in the cqlite fork.** `backend/dist/` holds one abi3 wheel per architecture in Git LFS, and `backend/Dockerfile` verifies the checksum beside it before installing; nothing in the backend image compiles.  The source is `cqlite-datafusion/`, a nested workspace on `mck/open-htap-stack` in [thelastpickle/cqlite](https://github.com/thelastpickle/cqlite), beside the patched `cqlite-core` it reads below, and `backend/dist/VENDOR.md` names the commit each wheel came from.  cqlite's own `arrow` feature is left off on purpose: `RecordBatch` appears in cqlite-core only under `src/export/`, above the query layer, and this crate reads below it, so the feature would add a `HashMap` per row and mean leaving `KWayMerger`.

The trade that arrangement makes is worth knowing before changing the reader.  A reader change now costs a fork commit, a wheel build for both architectures with the amd64 one under emulation, and a commit here; in exchange the backend image builds in seconds rather than the 9m25s it took when it compiled 313,000 lines of Rust, and CI no longer pays that on the scheduled run where no layer cache exists.

The reader reads `cassandra-data/` mounted read-only, in the backend's own process, and its answer is as of the last flush: an unflushed table has no file, so the path declines rather than returning nothing, and `data_age_s` says how far behind the answer is. Registration needs Cassandra once, for each table's `CREATE TABLE`, so the reader cannot parse files with a schema the cluster has since changed.

**A predicate that names partitions is pushed into the reader.** The fork's `cqlite-datafusion/crates/cqlite-datafusion/src/predicate.rs` recognises equality and `IN` on every partition-key column, and reports those filters `Exact` so DataFusion drops them; the scan then seeks to each key through the BTI trie instead of walking the table and discarding rows. Measured on `ea`: one shard of a 15-minute window took 818.5 ms where a walk of the same 4 generations of 488,777,346 bytes took 24.9 s; on a much larger `da` table it was 3.7 s against 539 s. The named keys go to their merger a few at a time, one by default, because that is what bounds the memory: cqlite's seek merger decodes every row of every partition it is given before the merge starts. A window of 16 partitions read together held 4.84 GB of anonymous memory for 1,246,271 `ea` rows and 6.83 GB for 1,779,134 `da` rows, near enough 3.9 GB per million rows on either file set, against 1.09 GB and 1.41 GB read one at a time. One at a time was also faster, 11.3 s against 14.3 s under sampling on `ea` and 23.7 s against 39.0 s on `da`. The walk has no such cost, because `KWayMerger` streams: 1,714,500 `ea` rows over 304,168,186 bytes held 0.11 GB, and 25,234,785 `da` rows over 4.64 GB of files held 0.15 GB, where the idle process holds 0.10 GB. The container's 8 GB limit is what keeps that seek growth off the host: a second window read with all 16 partitions in one merger crossed it on the `da` files and the kernel killed the backend, and before the limit existed it killed uvicorn three times in one afternoon, at 11 to 13 GB, with the host choosing the victim.

**The reader applies the token bound itself, twice, because cqlite drops it.** `ScanTokenBound` is documented as a pushdown hint the consumer must enforce, and a generation this stack writes is BTI, at `da` and at `ea` alike, which fails the gate on cqlite's Summary-guided walk and drains through the stitch-and-parse window instead; that route takes no bound.  `scan.rs::in_slice` tests the partition's token at the merge boundary, and that test is the guarantee: before it, four slices over a 100-row table returned 400 rows, and after it 100 rows at 1, 2, 3, 7 and 16 slices, agreeing with CQL.  `TokenGate`, in the fork's `cqlite-core/src/storage/sstable/reader/data_access/summary_scan/mod.rs`, applies the same bound far earlier, at the one emit both fallback routes pass through, so an out-of-slice row is never converted into a `MergeEntry`.  An equivalent gate in the merge producer saved 43% of the work a slice repeats on one `da` generation, 16.14 s of CPU to 9.14 s, and held peak resident at 35 to 39 MB where seven slices had reached 716 MB; `TokenGate` filters one layer earlier still, so read those as the floor.  The second test stays because `ScanTokenBound` is a hint the consumer must enforce and the provider is published against a registry `cqlite-core` that carries no gate.

**`cqlite_splits` stays at 1 because most of a slice is work every other slice repeats.** The BTI route drains the data section sequentially with no partition-index seek, so each slice re-reads and re-parses the whole file and only the row decode divides.  Swept once per SSTable version, and the direction is the same on both: N× the CPU buys no wall clock.  Two `ea` generations of 180,672,491 bytes took 9.53 s, 14.05 s, 23.83 s and 38.68 s of CPU at 1, 2, 4 and 7 slices, with the wall clock rising from 14.05 s to 17.34 s; one 203.7 MB `da` generation of 1,102,576 rows took 11.79 s, 22.05 s, 40.33 s and 73.01 s, its wall clock 6.0 to 7.4 s at one slice against 11.2 to 12.4 s at seven.  Solving N·P + R from the 2- and 4-slice points puts the repeated share at 53% on `ea` and 71% on `da`, so read it as a majority and not a constant: each is one sweep, and what makes the two differ has not been measured.  Memory is not the reason, which earlier notes here had wrong: the seek path is what holds rows, and splits divide only the walk, whose merger streams.  Raising this waits on a walk driven from `Partitions.db`, which is a new range-scan route in cqlite rather than an added parameter.

**Read `anon` from the cgroup, not `memory.peak`,** when attributing a cqlite query's memory.  A walk charges the page cache of every file it reads to the backend's cgroup, 4.19 GB of it for the whole table, and a memory limit counts those pages although the kernel reclaims them rather than killing for them.  `memory.peak` sums the two, and reading it alone made a walk that holds 0.15 GB look as though it held 4.37 GB.  `scripts/cqlite-memsample.sh` samples `memory.stat` while a statement runs; a sample costs two `podman exec` calls, so it stretches a wall clock and the timings come from an unsampled run.

**A clustering-predicate row skip was measured and not built.** Skipping `assemble_read_cells` and the Arrow append for an excluded row can save only what those cost, and over one shard of a window they are 8.5% of the merge: three paired runs of 111,841 rows averaged 1359.0 ms with no column assembled and 1474.5 ms with ten.  The merge is the other 91.5%, and during a walk it runs at 0.78 of a core out of seven with no block-device reads at all, so the constraint is the single-threaded merge rather than either I/O or row assembly.

**The partitioner is Murmur3 and cannot be changed.** `cassandra/entrypoint.sh` reads `CASSANDRA_PARTITIONER`, so the switch exists; it was measured and the answer is no. On ByteOrderedPartitioner three of the demo's features refuse outright, and two of the refusals are inside libraries this repository does not own. `ensure_schema()` cannot finish: SAI is Murmur3-only ("Storage-attached index does not support the following IPartitioner implementations"), it is the only vector index Cassandra has, and being the schema step its refusal stopped the sink with three of eleven tables created. `spark` refuses with `IllegalArgumentException: Unsupported partitioner`, and `spark_bulk` with `UnsupportedOperationException: Unexpected partitioner` at `org.apache.cassandra.spark.data.partitioner.Partitioner.from` — an enum of Murmur3 and Random, so not configuration. `cassandra`, `presto`, `cqlite` and Accord itself all worked under BOP; the price is two access paths and the vector search page. The switch stays because a BOP cluster elsewhere may still be wanted, GEICO's `cassandra-sql` requiring one; it is not a thing to turn on here. Separately, `num_tokens=1` costs nothing observable: a full dashboard run on Murmur3 with one token passed every check, so a partitioner spike need not treat the token count as a confound.

**Accord is on, and `transactional_mode='full'` reaches further than `BEGIN TRANSACTION`.** Six tables opt in — `sessions_open`, `session_seq_applied`, `session_timeline` for the sequence demo, and `zone_occupancy`, `zone_clearance`, `drone_clearance` for the clearance one — and `events` deliberately does not. `full` routes *every* read and write to an opted-in table through Accord, so a plain `INSERT` and an ordinary `SELECT` are both refused at the driver's default LOCAL_ONE: "ConsistencyLevel LOCAL_ONE is unsupported with Accord for write/commit". Opting `events` in would therefore have broken every dashboard read of it as well as putting consensus in front of 2,000 writes a second; `execute_write` and `_timeline_rows` use QUORUM `SimpleStatement`s rather than changing `execute_query`'s global default. A transaction must also be **deterministic**, so every timeuuid and timestamp is bound by the caller with `uuid_from_time`; `now()` would be evaluated per replica. And an Accord transaction returns **no `[applied]` column**, only the row its own `SELECT` projects, so `backend/app/routes/transactions.py` derives `applied` and the refusal reason from the guard values and CI asserts the row count rather than the field. The option cannot be added to an existing table, which costs a wipe to learn. It *can* be read back, contrary to what this file said before: `system_schema.tables` has no such column, but `DESCRIBE KEYSPACE demo` works through the Python driver, server-side in one round trip, and returns 16 rows — the keyspace, its 14 tables and its one index — each with a `create_statement` carrying the option, six reading `full` and eight `off`. `backend/app/routes/schema_explorer.py` reads it that way and takes the key structure from `system_schema.columns` beside it. An earlier note here said a script must parse `DESCRIBE` output or ask behaviourally without establishing that the first works; it does, and the `schema` skill now has both forms. The behavioural probe stays on `/api/transactions/session/schema` on purpose: a refused transaction is the node refusing, where a `create_statement` is the node describing.

**The clearance semaphore counts down because Accord will not compare two `LET` references.** `IF occ.granted < occ.capacity` raises `SyntaxException … IllegalArgumentException null`, so `_grant_cql` holds a decrementing `remaining` and tests `occ.remaining > 0`; the counter's agreement with the holder rows is then checked on every response as `capacity == remaining + holders` and reported as `consistent`. The demo's seven outcomes are what the transaction is for, and the contention route is the claim: 8, 16 and 32 concurrent askers against a capacity of 2 each granted exactly 2, with no errors and with different winners between runs. Measured over 100 repeats, a grant's p50 is 1.31 ms and a release's 1.24 ms. The sink owns the capacities, so an assertion reads `capacity` from the response rather than naming 2.

Measured over four runs of 2,000 applied transactions, the median is stable and the maximum is not: 1.66 – 1.87 ms for the transaction, 0.83 – 1.00 ms for an `IF NOT EXISTS` lightweight transaction and 0.43 – 0.56 ms for a plain insert, against maxima of 6.2 – 26.7, 4.7 – 32.0 and 3.2 – 28.4 ms respectively. No path's tail separates from the others, so quote the medians and say the maxima are noise; one run alone had read as though the transaction's tail were the finding. All of it is one node at RF=1, which pays none of the round trip Accord exists to reduce, so it is a floor.

**Accord makes an unclean shutdown fatal, and the entrypoint has to say otherwise.** Accord writes a `started` marker into `cassandra-data/accord_journal/` and a `stopped` marker on a clean stop; finding the first without the second, `AccordService.localStartup()` throws "Stop marker is older than start marker (-1<…), so cannot assume we have a complete log of our votes in any consensus groups. Exiting." Every table's data is intact and the node will not open. A `podman machine stop`, a sleeping laptop or an out-of-memory kill each cause it. `cassandra/entrypoint.sh` therefore sets `accord.journal.stop_marker_failure_policy: ALLOW_UNSAFE_STARTUP`, and what that gives up is the guarantee that this node knows every vote it cast; at RF=1 there is no peer to hold a conflicting one, so **a multi-node cluster must not carry it**. The key is snake_case although the Java field is `stopMarkerFailurePolicy`, the enum is `EXIT` (the default) / `UNSAFE_STARTUP` / `ALLOW_UNSAFE_STARTUP` / `REBOOTSTRAP`, and both middle values reach the same branch; established by `javap`, because 6.0-alpha2 is installed from a binary tarball and there is no source here to read.

The failure was hard to attribute, and each way it hid is worth knowing. The container reported `Up (starting)` with nothing listening, because the entrypoint polled `cqlsh` against a daemon it had backgrounded and lost; that loop now tests `kill -0` and exits, so the container exits and its log ends at the cause. `spark` looked like a second, unrelated failure but had simply never been started, because its `depends_on` is `condition: service_healthy` and cassandra never became healthy: `State=initialized`, `StartedAt=0001-01-01`, an empty log. And neither the sink nor the backend recovers a dead session on its own — ten hours later the sink was still reporting "Unable to complete the operation against any hosts" with an empty error map, meaning no host left to try. The `stack` skill has the recovery.

**cassandra-sql is a sixth interface, not a sixth access path.** GEICO's cassandra-sql runs as `accord-sql`, and `backend/app/routes/sql_console.py` drives it on the SQL subtab of `/transactions`. Its five tables are this repository's own and are the fleet's — `operators`, `drones`, `zones`, `flights`, `flight_legs` — and the fleet names are naming rather than replication: no process copies a `demo` row into them, and GEICO's `demo-ecommerce.sh` schema that they replaced is gone from the code and from the docs. In its `kv` storage mode it keeps SQL rows in three keyspaces of its own — `cassandra_sql`, `cassandra_sql_internal`, `pg_catalog`, thirteen tables — under an ordered key-value encoding of its own, so it cannot read `demo.events` and it belongs in no comparison with the five paths; its `schema` mode can read native tables but documents "No transactions", "No JOINs or subqueries" and "Eventual consistency only", which is weaker than the Presto path already here. Its own tables are Accord tables, `transactional_mode = 'full'`. Three facts about running it. 5432 is `private static final` in its source and not configurable whatever its README implies. **One patch is needed**, in `accord-sql/patches/`, because `CassandraExecutor` hard-codes `localhost:9042` in a second session and its unconditional `@PostConstruct` fails the bean in a container; the patch gives it the four properties `CassandraConfig` already reads, and is worth upstreaming. **The partitioner needed no patch** although its prerequisites demand ByteOrderedPartitioner — no code under `src/main/` reads the partitioner, the one range scan is legal under Murmur3, and row order is discarded anyway; `CassandraConfigTest` does assert the byte-ordered partitioner and so fails here, which is why the build runs `-x test`. That matters because byte-ordered partitioning was measured here and rejected for the cluster: storage-attached indexes refuse it, and so do the spark-cassandra-connector and the CEP-28 bulk reader, inside libraries this repository does not own.

**Seven cassandra-sql behaviours are measured, and three of them shaped the interface.** A bound parameter of an integer type returns no rows and raises nothing, while binding the same value as a string returns the row, so the console offers no parameters at all. `COUNT(*)` over an empty table raises "Aggregation failed: Index 0 out of bounds for length 0", and inside a `UNION ALL` that failure takes the whole statement with it, so `/tables` counts one table per statement. An `UPDATE` that does arithmetic rewrites an integer column as a double, where one assigning a literal does not, `DECIMAL` is held as a double, and every value arrives as text; so a CI assertion on a number compares through `float()`. Of the declared constraints only `UNIQUE` is enforced: a duplicate primary key upserts, and `FOREIGN KEY`, `NOT NULL` and `ENUM` are each accepted and ignored. Two claims recorded here earlier were wrong and are corrected in the code comments: `UNION ALL` is *not* broken, and it is arithmetic rather than every number that produces a double.

**Four more are join defects, and every preset is written around them.** A column name held by two joined tables resolves to one table for the whole statement and an alias does not help, so `l.distance_km` answers the flight's 21.4 for both legs where dropping the `flights` join answers 6.2 and 15.2; `ORDER BY` is ignored on a grouped result; binary arithmetic across two joined tables returns its right-hand operand and discards the operator, so `SUM(l.dwell_min * z.fee_per_min)` answers the fees; and arithmetic against a literal inside a join projection drops the column, so a client reading by position gets a different one. Single-table arithmetic and single-table `ORDER BY` are both exact, which is what places all four in the join. `/api/sql-console/quirks` reproduces each beside a single-table control, and **CI prints them and asserts nothing about them**, because an assertion on a defect fails on the release that fixes it; it does assert each control, since a control that raised would leave its probe evidencing nothing.

**Judge a `/reset` by its `CREATE` and `INSERT` statements, not by `error_count`.** `DROP TYPE` ignores its `IF EXISTS` and raises where `DROP TABLE IF EXISTS` and `DROP SEQUENCE IF EXISTS` are silent, and `DROP INDEX` is unimplemented in both forms, answering "Unsupported SQL type"; a `DROP TABLE` is what removes an index. So a reset on a stack whose ENUM types are absent reports 2 errors and 23 successes, and two states produce that: a first-ever reset, and **a restarted `accord-sql`, which keeps its tables and loses its ENUM registry** — after a restart the five `DROP TABLE` statements each took real time and succeeded while both `DROP TYPE` statements reported the type missing. Asserting `error_count == 0` there would have failed CI on every fresh stack. Separately, `UNIQUE` is the one constraint this engine holds, so the seed is not idempotent: a second `POST /schema` is refused with "UNIQUE constraint violation: operators_licence_unique", which is why `/reset` exists at all.

**A failed `accord-sql` start does not stop its JVM, so the entrypoint has to.** `CassandraExecutor.init` issues its `CREATE KEYSPACE IF NOT EXISTS` inside one driver request budget, and the driver's default is 2 seconds; against a Cassandra that had only just opened its port the request answered too late and the bean failed the application with "Cannot connect to Cassandra", caused by "Query timed out after PT2S" at `init:65`. `depends_on: service_healthy` does not prevent it, because a node that answers `cqlsh` is not thereby a node that answers a schema change in two seconds. The Spring context then died and the JVM lived, because the driver's Netty threads are not daemons: podman reported the container running with `Restarts=0`, nothing listened on 5432, `restart: unless-stopped` never fired, and `podman compose up -d --no-deps accord-sql` answered "Container accord-sql Running" and changed nothing. Two changes fix it. `JAVA_OPTS` carries `-Ddatastax-java-driver.basic.request.timeout=30s`, which reaches both of the application's sessions — measured, not assumed: a run with `=1ms` printed "timed out after PT0.001S" from `s0` and `s1` alike — and costs a statement that would have failed at 2 s failing at 30 s instead. And `accord-sql/entrypoint.sh` waits for the Postgres listener, killing the JVM and exiting non-zero if 5432 stays closed for `ACCORD_SQL_STARTUP_TIMEOUT_S`, 300 by default, so the restart policy can try again. Both branches were exercised: a 1-second window killed a healthy start at 7.4 s, an unresolvable contact point exited at 12.5 s, and a normal recreate reported the listener open with `Started CassandraSqlApplication in 3.292 seconds`.

**`pg_tables` is stale and `pg_class` is not.** `pg_tables` and `pg_indexes` still list the dropped ecommerce tables and their indexes long after a `DROP`; `pg_class WHERE relkind = 'r'` and one `pg_attribute` read per `oid` are accurate, giving exactly the five live tables and their 40 columns in `attnum` order. So `backend/app/routes/schema_explorer.py` reads the second pair, never the first, joins in Python because this engine's joins are the four defects above, and reports the staleness as a warning rather than hiding it. Three more gaps come back the same way: there is no `information_schema`, `pg_constraint` is empty so `UNIQUE` is the one constraint enforced and the one the catalog does not report, and `pg_enum` and `pg_sequence` do not exist although the schema declares two ENUMs and a sequence.

**`pg_attribute` exists only after a `CREATE TABLE` has run in that JVM,** which makes the schema explorer's CI step depend on the cassandra-sql one before it. `PgCatalogManager` logs "tables will be created on first use", and it means it: a restarted `accord-sql` answers "Table does not exist: PG_ATTRIBUTE" to every read while `pg_class` still answers its five rows, so `/api/schema/sql` reported all five tables with no columns until one `CREATE TABLE` ran. `POST /api/sql-console/reset` is that `CREATE`, and after it the read returned the 40 columns again. `DROP TABLE` neither unregisters the view nor removes the rows, so the five tables created twice held 80 attribute rows for their 40 live columns; the per-`oid` read is indifferent to that, because a new table gets a new `oid`. What a `DROP` does leave behind is `pg_indexes`, permanently and across a restart: a `catalog_probe` table created for two statements is still listed there, a `DELETE FROM pg_indexes` reports success and changes nothing, and the row is not among the first 400 of `cassandra_sql.kv_store` under any readable key. So the explorer's staleness warning now names a table this repository made, which is the warning working rather than a fault.

**One comparison runs at a time** (`backend/app/routes/query.py`): two overlapping runs would each be timed while the other ran. The lock records what is running, so the Health page can show and cancel it. Cancelling a Spark query means closing its socket (`shutdown(SHUT_RDWR)`, not `close()`) *and* killing the job group via the Spark UI REST API — HiveServer2 leaves jobs running otherwise.

**The live embedder runs behind the writes, never in them.** `backend/app/routes/vector.py` can keep `drone_text_embeddings` following the snippets the sink writes: it re-reads them every five seconds and embeds the ones whose text changed, holding one digest per asset in memory so an unchanged snippet costs nothing. Embedding in the sink instead was rejected twice over: it would put an embedding call, and with a key a network round trip, in front of every write; and it would make the data path depend on the dashboard, where today either dashboard service can be stopped without touching ingest. The toggle is off at startup so that turning it on is what shows the point read staying put. Measured at a hundred assets: a pass of 32 to 97 ms, and p50 1.9 ms against a 2.6 ms reference over ~237 reads each.

**CDC is configured in three files and no one of them is enough.** `cassandra/entrypoint.sh` patches `cdc_enabled`, `cdc_raw_directory`, `cdc_total_space` and `cdc_block_writes` into `cassandra.yaml`; `ingress/consumer/consumer.py` declares `cdc = true` on `demo.drone_latest_status` and reconciles it on every start, because `cdc`, unlike `transactional_mode`, can be added to an existing table; and `cassandra/seed-cdc-configs.sh` writes the publisher's own settings as two rows of `sidecar_internal.configs`, a table the Sidecar creates itself, so a stack with no rows publishes nothing and says only "config is not ready". One table opts in and `events` deliberately does not, for the same reason it stays out of Accord. Apicurio holds the Avro schema rather than `cp-schema-registry`, which is under the Confluent Community License; its Confluent-compatible endpoint is `/apis/ccompat/v7`, and one subject `cdc-mutations-value` holds one schema at id 1. A fourth file matters for cost rather than for behaviour: `cassandra/sidecar-logback.xml` holds `org.apache.cassandra.cdc.kafka.KafkaPublisher` at WARN, because at INFO it prints one line per mutation carrying the whole row, `text_payload` included, about 2,000 lines a second of roughly a kilobyte each on the node's own console appender. `CdcSchemaSupplier` stays at INFO although it repeats twice a second, because its line is the counter-column refusal reporting that the fork's workaround fired.

**The CDC delay is not the commit log segment, and the publisher's state is what decides it.** `micro_batch_delay_millis` is 500 ms and neither figure below is that. At 2,000 events a second the p50 is 8.0 s over 26 one-minute samples, ranging 2.7 to 21.1 s; at 400 it is 2.2 to 4.7 s over ten samples, maximum 2.7 to 5.5 s, taken with the backend restarted so the tail was freshly attached and the publisher current. **Lower at the lower rate**, which refutes the segment-fill explanation these notes carried before: segments completed 45 to 46 s apart at 400 against 9.3 s at 2,000, so a mutation waiting half a segment would have shown about 23 s. The reader therefore consumes a segment as it is written, which is what CEP-8's per-segment index file is for; that much the two rates establish, and the mechanism was not instrumented, so do not attribute a figure to it. Quote a delay with its rate and the publisher's state beside it. Quote the publish rate from the topic's end offsets, 2,718 records/s over 1,447 s, and not from `rate_per_sec`, which `backend/app/routes/streaming.py` computes between two polls and so measures the consumer; its samples ranged 141.6 to 15,840.4 over the same steady stream.

**Either figure holds only while the writer is slower than the publisher, and that is not the demo's usual state.** The publisher's ceiling is the same order as the node's own write rate to the CDC table, so the queue moves either way depending on what the sink is doing: 4,144 and 4,349 records/s published against about 2,010 writes/s while it drained a queue it had built, then 2,410 published against 3,148 written while the sink drained its own Kafka backlog after a restart. A ratio above 1 is the publisher catching up and below 1 is it falling behind; neither is duplication, which was checked over a contiguous 200,001-record slice of the topic and is absent. Under a sink backlog the age of the newest published record reached 92 to 156 s in one run and 400 to 480 s in another, and it did not recover on its own within 480 s of observation. So **quote a delay as the best case and not as the demo's latency**, and say which rate and which state the stack was in when a figure was taken.

**An age once built stays, because the publisher's margin over the writer is a few percent.** A third window measured that directly, on a stack whose sink was draining a 528,921-record Kafka backlog after a Cassandra recreate: over 183 s the topic took 2,882 records/s against the sink's 2,703 writes/s, a ratio of 1.07, while `latency_p50_ms` held at 836 to 848 s across four samples 2 minutes apart and moved neither way. At 848 s and that rate the publisher was about 2.44 million records behind, and 179 records/s of margin would need some 3.8 hours to close it. So a ratio above 1 says the age will fall and not that it has; the sink's own lag drained from 528,921 to 104,621 over the same period, so the two backlogs recover on quite different timescales.

**`latency_*_ms` reports the age at Kafka append, so it measures the publisher and not the tail.** `age_ms` is a record's `kafka_at_ms` less its `mutation_at_ms`, both carried on the record, which is why it stays valid when the backend's own consumer is behind; an earlier note here called it the age at decode time. The exclusion of backfilled records is narrower than it looks, though: `_backfill_until` is fixed at attach, so a tail that falls behind afterwards counts old records as live. Restart the backend before quoting the field, and read `consumed` as a count since attach rather than as an offset.

**At the `cdc_raw` bound the node deletes and says so only at DEBUG.** `cdc_block_writes: false` was chosen because the two defaults deadlock: Cassandra forbids the segment that would take the directory past the Sidecar cleaner's own threshold, so the cleaner never fires and every write to `demo` is refused, measured at 4,261,415,150 bytes in 127 segments. With it false the directory held at 4,261,513,459 bytes in 129 segments, twenty-four segments were deleted, and both publication and the request path continued. Nothing in the log says a change was lost: "Freed up … in non-blocking mode" is issued through `Logger.debug`, established by disassembling `CommitLogSegmentManagerCDC$CDCSizeTracker`. What is observable at INFO is the oldest segment's name advancing, so assert on that rather than on a log line.

**The Sidecar's heap is 2 GB and nothing in this repository says so, which is how a CDC setting failed the `spark_bulk` access path.** `cassandra/entrypoint.sh` starts the Sidecar with no `-Xmx`, so `MaxRAMPercentage` gives it 25% of the container's 8 GB limit, exactly 2147483648 bytes, beside a Cassandra holding `-Xmx4G` in the same cgroup. `BufferingCommitLogReader` buffers a whole 32 MiB segment, and `max_commit_logs` decides how many at once; at 4 the heap ran out on one segment, `CommitLog-9-1787754521924`, and every one of the run's 27 `OutOfMemoryError: Java heap space` was on that same segment, because the reader retried it without advancing its high water mark and streamed it 220 times over `/api/v1/cdc/segments`. The garbage-collection thrash then stalled threads that have nothing to do with CDC: `sidecar-worker-pool-19` blocked 290,646 ms inside `RingProvider.queryRack`, and the Sidecar answered its own `request_timeout: 5m` with a 408 on `GET /api/v1/cassandra/ring/keyspaces/demo`, which is the call `CassandraDataLayer.initialize` makes. So the dashboard's `spark_bulk` path failed after 307,503 ms with a Sidecar timeout, and it is a race rather than a rule: an earlier step's bulk read passed at 14:39:04 while the Sidecar had been looping since 14:35, and the 14:39:51 request lost. `max_commit_logs: 2` is the fix and 2 is also the floor, since at 1 the reader publishes nothing at all: 3,758 writes a second reached the table and 0 records reached the topic over 183 s, while it polled the segment list about ten times a second. Because all 27 failures were on one segment, read this as peak heap lowered rather than as a segment proven readable; the untried lever is an explicit `-Xmx` for the Sidecar, which wants headroom the 8 GB limit does not obviously have.

**A CDC-enabled node cannot replay its commit log, so `nodetool drain` before every stop.** `CommitLogReplayer.handleCDCReplayCompletion` runs for each replayed segment that held a CDC mutation, and its `CommitLogSegment.writeCDCIndexFile` fails writing an 18-byte index file: `java.io.IOException: Bad file descriptor` at `BufferedDataOutputStreamPlus.doFlush`. `DefaultDiskErrorsHandler` then logs "Exiting due to error while processing commit log during initialization" and the node exits, with every table's data intact and 179 segments waiting. It is reproducible across restarts and it is not disk space, with 63 GB free, nor the bind mount, since the same 18-byte write from a shell into the same directory through the same mount succeeds; measured on darwin/arm64 only, so do not assume it on Linux. Two recoveries, both established here. `CASSANDRA_CDC_ENABLED=false podman compose up -d --no-deps --force-recreate cassandra` skips the path entirely, because `sawCDCMutation` gates the call, and the node replays and opens; `nodetool drain` then leaves one commit log segment and seven files in `cdc_raw`, after which a normal recreate with CDC on comes up in 55 s. What a drain gives up is the mutations in `cdc_raw` that the publisher had not yet read. CI is unaffected, because it brings the stack up once and never restarts the node.

**One commit log serves every table, so the CDC reader's schema must know every table.** Two demo columns defeat that, and each needed a fix outside this repository. A `counter` column made `AbstractSchemaBuilder` refuse the table, so the Sidecar fork registers such a table with the refused columns as `blob` and CDC off. A `vector<float, 1536>` column cannot be repaired that way at all: driver 3.x cannot parse the type, so the table never reaches the builder, and `blob` would be byte-wrong because `VectorType.valueLengthIfFixed()` is positive. The mutation therefore has to be skipped, and on 6.0 the reader's skip never fired: `PartitionUpdateSerializer.deserialize` rethrows `UnknownTableException` wrapped in `CoordinatorBehindException`, so `catch (UnknownTableException)` missed it and the segment was re-read forever. `69add7b` in the analytics fork walks the cause chain instead; `cassandra/dist/VENDOR.md` carries the whole chain and the bytecode each step rests on. Verified by writing 100 rows of the vector table on the fixed build: the tail advanced across the write and `CommitLog unrecoverable error` stayed at zero, where the unpatched build logged 146 in one minute and froze publication for eight.

**Reported figures are labelled with what they measure.** `snapshot_bytes` is the size of the snapshot a bulk read was taken over, and `sstable_bytes` the size of the live files a cqlite read opened; neither is what the read consumed when the statement names partitions, so a MB/s rate is quoted only for a statement with no `WHERE`. Likewise the compare presets group by `event_type` and keep five of the twenty types, ordered by name, so the sum of their rows is about a quarter of the window rather than its total. Both mistakes have been made here and corrected; see the `measure` skill for how each was caught.

## Conventions

Comments explain **why**, and record measurements and rejected alternatives where they would otherwise be re-litigated; several in `podman-compose.yml` and `spark_client.py` exist because the obvious setting was tried and measured worse. Match that density rather than stripping it.

Prose in docs and UI copy follows Strunk and White, two spaces after a period, semicolons and colons over em dashes, and no hard wrapping in markdown. State limitations plainly — the demo's credibility rests on the awkward numbers being present.

Editing `podman-compose.yml`: the Spark `command` is one single-quoted shell string, so an apostrophe anywhere in it, comments included, truncates the script; and compose interpolates `${...}` everywhere, comments included, so a shell variable needs its dollar doubled.

## Language rules

- **Terminology taboos.**  Do not use "canonical", "cache", "bearing", "substrate"; name the precise thing instead (the source, the pinned projection, the memoised value, and so on).
- **Expand an acronym on first use** in a document, then use the bare form.
- **Avoid Negative parallelisms:** "It's not X, it's Y." As in: "It's not a product launch. &emsp;It's a paradigm shift." This is rhetorical construction, and is rarely of value.
- **Avoid Rule of threes:** "Innovative, transformative, and groundbreaking." &emsp;Avoid defaulting to triplets when listing anything: adjectives, benefits, takeaways.
- **Avoid False ranges:** "From intimate gatherings to global movements." &emsp;"From technical expertise to creative vision." &emsp;The structure implies a spectrum, but there's no actual spectrum. &emsp;These are just loosely related things dressed up to sound comprehensive.
- **Avoid Compulsive summaries:** "Overall," "In conclusion". I.e, the tendency to restate what was just said, even when the passage is too short to require it. &emsp;Human writers sometimes do this in long documents, its use should be rare.
- **Use terminology accurately.**  Follow the ASD-STE100 Standard for Technical Documentation.  All terminology terms that has appeared with a specific technical meaning and context should thereafter not be borrowed. Avoid AI typical vocabulary: delve, intricate, tapestry, pivotal, underscore, landscape, foster, testament, enhance, crucial.

## House writing style

- English per Strunk and White's *The Elements of Style*.
- Favour semicolons, colons, and commas over em-dashes.
- Do not hard-wrap lines in markdown or other prose documents.
- Keep paragraphs to 1-4 sentences (essay style, introduce one concept per paragraph, prefer sentences short and active in voice and use more paragraphs). 
- Two spaces after a sentence-ending period; write the second as `&emsp;` in markdown.
